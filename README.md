# התזונה שלי — Personal Nutrition

אפליקציית תזונה אישית: תוכנית ארוחות, יומן ארוחות, שתייה, פעילות ומשקל. בעברית ו-RTL, בהשראת היכולות הציבוריות של Diet Angel (ללא שימוש בלוגו, תוכן או נוסחת הכוכבים שלהם — אלה לא ידועים ולא מומצאים כאן).

## טכנולוגיה

- React 18 + TypeScript + Vite
- Tailwind CSS (RTL, עיצוב מקורי)
- React Router
- Supabase (Postgres + Auth + Storage) — עם מצב הדגמה מקומי כשאין חיבור
- Recharts לגרף המשקל
- PWA (manifest + service worker דרך `vite-plugin-pwa`)

מבנה הקוד מפריד בין תצוגה (`src/components`, `src/pages`), שכבת שירותים (`src/services`) וגישה לנתונים (`src/services/supabase`, `src/services/demo`). כל מסך פונה אך ורק לשכבת השירותים (`src/services/index.ts`), כך שאפשר להוסיף בעתיד ספק נתונים נוסף (כולל שכבת AI) מבלי לפזר קריאות API במסכים.

## הפעלה

```bash
npm install
npm run dev
```

האפליקציה תיפתח בכתובת שמודפסת בטרמינל (בדרך כלל `http://localhost:5173`).

בלי חיבור ל-Supabase, האפליקציה עולה **אוטומטית במצב הדגמה**: המשתמש נכנס בלחיצה אחת, כל הנתונים נשמרים מקומית בדפדפן (`localStorage`) ומופרדים לגמרי מנתוני חשבון אמיתי. מצב זה מסומן בבירור בפס עליון כתום בכל מסך, ולא מבקש מידע בריאותי אמיתי.

## חיבור Supabase (מצב אמיתי)

1. צרו פרויקט חדש ב-[supabase.com](https://supabase.com).
2. בתיקיית הפרויקט: `cp .env.example .env.local` ומלאו:
   - `VITE_SUPABASE_URL` — מתוך Project Settings → API
   - `VITE_SUPABASE_ANON_KEY` — מתוך אותו מסך (ה-anon/public key בלבד; לעולם לא ה-service role key)
3. הריצו את ה-migration שנמצא ב-`supabase/migrations/0001_init.sql` על מסד הנתונים:
   - הכי פשוט: העתיקו את תוכן הקובץ להרצה ב-SQL Editor בלוח הבקרה של Supabase, או
   - דרך ה-CLI: `supabase link` ואז `supabase db push` (דורש [Supabase CLI](https://supabase.com/docs/guides/cli) מותקן ומחובר לפרויקט).
4. ודאו שב-Authentication → Providers מופעל Email/Password (זו ברירת המחדל).
5. הפעילו מחדש את שרת הפיתוח (`npm run dev`). האפליקציה תזהה את משתני הסביבה ותעבור אוטומטית למצב אמיתי — הפס הכתום ייעלם ותוצג מסך התחברות/הרשמה עם אימייל וסיסמה.

### מה ה-migration יוצר

טבלאות: `profiles`, `meal_plans`, `planned_meals`, `meals`, `meal_items`, `water_logs`, `activity_logs`, `weight_logs`, `favorite_meals` — עם אילוצים (כמויות חיוביות, ימי שבוע 0–6, מניעת מדידת משקל כפולה לאותו יום, מניעת רישום יומן כפול מאותה ארוחה מתוכננת), אינדקסים, טריגר `updated_at`, **RLS מלא** לפי `auth.uid()` בכל טבלה (כולל `meal_items` דרך הבעלות של הארוחה האם), ו-bucket פרטי בשם `meal-photos` עם מדיניות גישה לפי תיקיית המשתמש בנתיב.

## מבנה נתונים ותמונות ארוחה

כשה-Storage מחובר, ניתן לצרף תמונה לארוחה ביומן. הקובץ נשמר בנתיב `<user_id>/...` ב-bucket פרטי, ותצוגה מתבצעת דרך Signed URL זמני (10 דקות) — לא URL ציבורי קבוע.

## מה מומש בגרסה הראשונה

- כניסה/הרשמה (Supabase Auth) או כניסה למצב הדגמה.
- שאלון היכרות קצר (שם, מטרה, העדפות, לא-אהובים, אלרגיות, משקל פתיחה, יעדי שתייה/פעילות — כולם אופציונליים חוץ משם).
- **היום שלי**: סיכום שתייה/פעילות/משקל אחרון, ארוחות מתוכננות להיום מתוך התוכנית (עם "אכלתי ✓" שמעביר ליומן ומונע כפילות), ארוחות שנרשמו, פעולות מהירות.
- **יומן**: ניווט בין ימים, הוספה/עריכה/מחיקה/שכפול של ארוחות, רישום ומחיקה של שתייה ופעילות.
- **התוכנית שלי**: תכנון שבועי לפי יום ראשון–שבת וסוג ארוחה, העתקת יום שלם ליום אחר, העברת ארוחה מתוכננת ליומן בתאריך נבחר.
- **התקדמות**: גרף משקל אמיתי (Recharts), שינוי בין מדידות רק כשיש שתיים ומעלה, סיכום 7 ימים אחרונים (ימים עם תיעוד, שתייה, פעילות) — ימים ללא תיעוד לא נספרים כ"לא אכל/לא שתה".
- **הגדרות**: עריכת פרופיל ויעדים, ייצוא כל הנתונים האישיים לקובץ JSON, התנתקות.
- מניעת שמירה כפולה בלחיצה חוזרת (מזהה בקשה בתהליך + אילוצי ייחודיות במסד הנתונים).
- RTL מלא, נגישות בסיסית (אזורי לחיצה ≥44px, `aria-label`, כיבוד `prefers-reduced-motion`), PWA עם אייקונים מקוריים.

## מה עוד לא נבדק

- שמירה בענן אחרי כניסה מחדש ובידוד נתונים בין שני חשבונות אמיתיים — **לא נבדק**, כי הסביבה הנוכחית אינה מחוברת לפרויקט Supabase. לאחר חיבור (ראו למעלה), מומלץ לבדוק ידנית: התחברות משני משתמשים שונים ואימות שכל אחד רואה רק את הנתונים שלו.
- העלאת תמונות אמיתית ל-Storage לא נבדקה מול פרויקט אמיתי (הקוד קיים ומוכן, אך רץ רק מול demo placeholder כרגע).

## מה דורש הגדרה מהצד שלכם

1. פרויקט Supabase + משתני הסביבה ב-`.env.local` (ראו מעלה).
2. הרצת ה-migration.
3. אם רוצים תמונות ארוחה: לוודא שה-bucket `meal-photos` נוצר (ה-migration יוצר אותו אוטומטית).
4. פריסה (hosting) אם רוצים גישה מחוץ למחשב המקומי — לא בוצעה כחלק מגרסה זו לפי בקשה.

## חיפוש מזון וחישוב קלוריות

האפליקציה כוללת חיפוש מזון עברי, זיהוי ברקוד וחישוב קלוריות/מאקרו אוטומטי בכל פריט ביומן ובתכנון, מבוסס על שני מקורות חינמיים:

- **מאגר התזונה הלאומי הישראלי** ([data.gov.il](https://data.gov.il)) — 4,624 מזונות עם ערכים ל-100 גרם ו-19,024 רשומות מידה ביתית (כף/כפית/גביע/יחידה וכו'), מיובאים מראש לקובץ [src/data/foodCatalogIsraeli.json](src/data/foodCatalogIsraeli.json) על ידי [scripts/import-foods.mjs](scripts/import-foods.mjs) ומשמשים כמאגר החיפוש המקומי (חיפוש תוך כדי הקלדה, ללא קריאת רשת).
- **Open Food Facts** — שליפת מוצר לפי ברקוד בזמן אמת דרך [src/services/foods/offClient.ts](src/services/foods/offClient.ts) (timeout, retry על 429/503, הגבלת קצב צד-לקוח).

### רישוי וייחוס

- נתוני Open Food Facts תחת רישיון **ODbL** (Open Database License) — כל שימוש חוזר/הפצה של נתונים שנשלפו מהם חייב לשמר את הייחוס הזה.
- מטא-הנתונים של מאגר התזונה הלאומי הישראלי מוצגים ב-data.gov.il כ-`Other (Open)`.
- הפרדה מלאה: קטלוג המזונות הוא נתון ציבורי (טבלת `foods`/`food_units` ב-migration `0002`), נתוני יומן/ארוחות פרטיים של משתמש נשארים בטבלאות הקיימות תחת RLS ולא מיוצאים כחלק מהמאגר.

### רענון המאגר וייבוא ראשוני

```bash
node scripts/import-foods.mjs
```

- ללא משתני סביבה — הסקריפט כותב מחדש את [src/data/foodCatalogIsraeli.json](src/data/foodCatalogIsraeli.json) בלבד (משמש גם את מצב ההדגמה וגם כברירת מחדל/גיבוי). זהו ה-upsert (`onConflict: source,source_id`) כך שהרצה חוזרת לא מכפילה רשומות.
- עם `VITE_SUPABASE_URL` ו-`SUPABASE_SERVICE_ROLE_KEY` (מפתח ה-service role — **לעולם לא בצד לקוח**) מוגדרים בסביבת ההרצה של הסקריפט (לא ב-`.env.local` של הדפדפן), הוא גם מבצע upsert לטבלאות `foods`/`food_units` ב-Supabase.
- התאוששות מייבוא שנכשל באמצע: הכתיבה לקובץ המקומי אטומית (קובץ שלם או כלום), וה-upsert ל-Supabase מתבצע בצ'אנקים של 500 עם `onConflict` — הרצה חוזרת של אותה פקודה משלימה בבטחה בלי למחוק את מה שכבר נכתב.
- קלוריות: שדה `food_energy` במאגר הישראלי כבר בקק"ל (לא קילוג'אול) — אומת ישירות מול המקור, לא הונח.

### אי-התאמות ידועות במקור (לא מוסתרות)

- קוד ממשלתי `8519` (לאבנה גד 5%) מציג 99 קק"ל, לעומת 87 קק"ל בברקוד המקביל ב-Open Food Facts. שני המקורות נשמרים בנפרד ולא ממוצעים — המשתמש בוחר את המוצר הספציפי (כולל המקור) בעצמו.
- מוצרים עם כמה גרסאות (למשל "לאבנה גד" — 5%/9%/עיזים) מוצגים כרשימת בחירה; החיפוש אינו בוחר אוטומטית וריאציה ספציפית ללא סימון ברור בטקסט החיפוש (למשל אחוז שומן).

## הרחבות עתידיות (נקודות עיגון קיימות בקוד)

- מעקב קבוצות מזון/מכסות: `meal_items` כבר מבנה גנרי (שם, כמות, יחידה) שאפשר להוסיף לו קטגוריה בעתיד בלי לשנות את שאר האפליקציה.
- שכבת AI: כל הגישה לנתונים עוברת דרך `src/services`, כך שאפשר להוסיף שירות AI חדש (למשל זיהוי מזון מתמונה) כמודול נפרד בלי לגעת במסכים.
- נוסחת כוכבים / דירוג: לא קיימת בכוונה בגרסה זו (אין מידע על השיטה המקורית) — כשתהיה זמינה, אפשר להוסיף שדה מחושב על בסיס `meal_items` הקיים.
- פענוח הטקסט החופשי ([src/lib/foodTextParser.ts](src/lib/foodTextParser.ts)) מבוסס כללים ומילון קטן (מותגים, יחידות) — לא הבנת שפה טבעית מלאה. משפט לא מוכר עובר לבחירה המובנית עם הטקסט המקורי, ולא מומצא לו ניחוש.
